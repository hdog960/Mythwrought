# Mythwrought developer efficiency

Use this procedure at the start of an existing assignment and when handing it off. The standing instructions are [one normal world creation flow](https://github.com/hdog960/Mythwrought/issues/492), [shared height](https://github.com/hdog960/Mythwrought/issues/498), and [efficient qualification](https://github.com/hdog960/Mythwrought/issues/501). The creator's current instructions and existing assignment define your permissions. The toolkit produces advisory reports.

## Continue development

1. Recover your identity, existing assignment and latest compact checkpoint. Read the registry entry and its source if present. For a lane missing from the registry, take your branch, PR, roadmap and role from your own instructions or the creator. The recorded historical lane intake is background. The current lane prompt is authoritative for its own assignment.
2. Run one continuation report for the branch and compare its exact GitHub HEAD and PR with the checkpoint. If either differs, identify what advanced before following the old next action. Use the previous main SHA to see only shared changes relevant to your assignment. Review affected owners and changes to protected refs. Unknown diff coverage requires manual reconciliation.
3. Authenticate existing results once. A pinned, qualified gate can be reused for its stated scope as allowed by creator policy and branch requirements. Review actual artifact contents when a gate requires visual inspection, failure details or performance measurements. A metadata match alone establishes the artifact's published identity. Leave an explicit reason for any new expensive run.
4. Batch a coherent change, run local syntax and affected native tests, and use a targeted browser or WebGL2 scenario for affected behavior. Refine the advisory plan for the actual changes. Whole app, shared integrations, unknown inputs and release scope can require the existing full gate. Existing branch requirements govern. Keep working on verified independent tasks if CI is pending. Record the exact pending ID and end the session once the next action depends on its outcome. A subsequent normal session may check that ID once when actionable.
5. Save a compact checkpoint in the existing owner handoff location. To opt into automatic lookup on a branch whose owner may commit handoffs, place the JSON in `docs/developer-checkpoints/<owner>.json` in a separate checkpoint-only commit immediately after the observed head. An external handoff can pass the same JSON explicitly. Keep it out of another owner's branch and avoid shared log edits during independent work. Capture the exact observed references, creator or roadmap revision, completed work and relevant files, authenticated gate names and links, pending run IDs, real blocker, remaining objectives and one authorized next engineering action. Run numbers stay linked to the commits that actually ran them.

## Choose your available surface

| Surface | Procedure |
|---|---|
| Codex, Git and Node | Use the repository launcher. Example `node tools/devkit/dev.mjs "Continue my development" --owner beasts`. If your branch predates the toolkit, use the centrally maintained launcher from a separate checkout while running it from the repository worktree. Use `--checkpoint <file>` when an owner checkpoint exists. |
| GitHub with workflow dispatch permission | From the default branch use **Actions → Developer toolkit report → Run workflow**. Choose an operation and supply your owner or existing branch and PR. Paste checkpoint JSON only when it is suitable for public job output. Read the run summary once. Use this for a missing report when it meaningfully advances work. The report workflow has read permissions and launches no qualification workflow. |
| GitHub browser or connector with read permissions | Read `tools/devkit/registry.json` from default branch. Open only your branch/PR and main, compare their full SHAs with the checkpoint, and inspect the existing run, attempt, job and artifact links. Match the workflow checkout, required executed steps and fixture. Record Missing when those facts are inaccessible. The GitHub Compare view or PR Files changed supports the same advisory system review. A hosted report may be requested through your existing authorized operator when necessary. |
| Conversation without direct repository access | Ask the conversation to use this procedure with an existing public report, owner checkpoint and exact GitHub links. Its results retain the observation time and can be used to resume when the current ref is available. Use `unverified` for live identity and qualifications that cannot be authenticated. The conversation can prepare a JSON checkpoint and identify the one missing observation rather than reconstructing the roadmap. |
| Scheduled `:00`, `:12`, `:24`, `:36`, `:48` | Resolve your current lane prompt and handoff first. Use your minute as owner and give the existing authorized branch/PR. Follow the same report or read procedure. Record the observed ref, work moved forward, gate reused or one pending ID, and next action. Keep existing assignments, schedule, permissions and merge restrictions. |

| Conversation request | Operation |
|---|---|
| Continue development, recover checkpoint, audit remaining roadmap | `continue --owner … --checkpoint …` |
| Authenticate existing tests | `evidence --head … --gate …` or `evidence --owner … --gate …` |
| Find existing exact head runs and failed job links | `runs --owner …` followed by the linked attempt. For one known run use `blocker --owner … --run …`. |
| Check shared changes or compatibility | `compatibility --owner … --base <previous-main-sha>` |
| Run only necessary tests | `plan --owner …`, then execute only justified tests using their existing harnesses. |
| Find my blocker | `blocker --owner … --checkpoint …`. With corroborating evidence use `--access permission`, `service`, `workflow`, `assumption` or `prerequisite`. |
| Generate a checkpoint | `checkpoint --owner … --next "…" --done "…" --remaining "…"`. Add `--gate`, `--pending`, `--protect`, `--blocker` and `--roadmap-version` as applicable. Redirect JSON to the existing lane handoff location. |
| Prepare a release candidate or check readiness | `release --owner … --gate … --base …` and complete the release review below. |
| Audit development efficiency | Read report counters and use the matching measures in the [pilot](DEVELOPER_EFFICIENCY_PILOT.md). |

The CLI accepts custom `--owner` and `--branch` for an existing assignment outside the registry. `--pr` verifies the live PR against the ref. `--head` supports historical analysis only. `--systems` adds a comma separated list of systems from your assignment when the existing checkpoint lacks them. Keep checkpoint text fields below 900 characters each. A browser or connector user can copy the same JSON field names from the CLI output example in the pilot.

## Evidence and blockers

The registry is a centrally reviewed index. Each onboarded assignment entry links to its source and records the known roadmap revision and handoff. Branch HEAD and PR state come from GitHub on each report. Roadmap revisions, owner identity and operating permissions remain with the original assignment. Discovery of an assignment or an evidence record conveys no permissions. Use one shared integration queue in the relevant issue or PR by agreement with existing owners.

`runs` returns up to 30 existing exact-head results and marks when more exist. `evidence` authenticates a reviewed gate by repository, exact attempt, workflow path and blob, candidate tree, environment declaration, fixture, executed job steps and artifact metadata. Known statuses are **qualified**, **pending**, **failed**, **stale**, **invalidated** and **missing**. A later attempt is a separate record. Qualified evidence names the source commit and scope even when reuse is eligible. A changed habitat input, fixture, runner assumption, workflow or unknown dependency requires requalification. The native mining example permits only the reviewed toolkit paths to differ. New gates default to exact candidates until owners review and register a complete dependency closure including dynamic imports, assets, test fixtures, configuration and runtime environment.

Use `evidence … --cache <directory>` only when archive bytes are required. It verifies the GitHub SHA-256 before storage and checks it again before reusing the archive. GitHub may require an authorized token for downloads. Configure credentials outside the command and checkpoint. Use the relevant job log to identify the first real failure before deciding whether it is a product failure, outdated fixture, wrong assumption, workflow problem or temporary runner issue. Keep infrastructure errors and the exact operation in the checkpoint. Repeated unchanged blockers call for a change in inputs or owner action.

## Release and publication

Use the existing integration queue to agree on the repository, expected base and head, affected owners, exact qualification inputs and creator decision. A coordinated release verifies one normal Create World, historical save and generator compatibility, shared height and owner budgets, actual installed upgrade and rollback, exact asset inventory and offline cold boot. Run the current manifest validator and the applicable real browser fixtures. Review the required aggregate and any manual gates. Keep the expected head and protected refs in the decision and recheck them immediately before any separately authorized merge.

After authorized release publication, capture the main SHA, Pages workflow and deployment for that SHA, live release identity and relevant live assets. With `release --branch main --publication <pages-run>`, the CLI checks the successful Pages run and compares six live shell asset blobs to current main. The full installed upgrade and historical-save gates still require their own evidence. Hand the physical iPhone reviewer the exact build/release ID, prior installed version, device/OS, scenario, expected behavior, performance criteria and evidence needed. Treat the creator decision and physical result as separate signed-off handoffs according to existing policy.
