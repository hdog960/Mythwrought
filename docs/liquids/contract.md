# Shared liquid contract v1 — isolated candidate (2026-11-27)
Owner: Business Water A. Branch `business/liquids/water-core`. Creator's five-liquid scope: water, lava, acid, Amber Sap, Liquid Resonance (not water). No tar. This is a usable isolated interface, not a production integration or a claim that every gameplay mechanic is implemented.

## Import and state
`src/liquids/core/engine.mjs` exports `LIQUID_IDS`, `CELL_CAPACITY=8`, `LIQUID_CONTRACT_VERSION=1`, `createLiquidEngine(options)`. Stable string IDs: `water`, `lava`, `acid`, `amber-sap`, `liquid-resonance`; do not assign global block IDs. Each lane exports an isolated descriptor `{id,gravityLimit,lateralLimit}`: integer limits 0..8 per visited cell; gravity first, then total lateral limit. Water A exports `WATER_DEFINITION` from `src/liquids/water/physics/definition.mjs`. Nonwater definitions must be supplied by their owners, not hard-coded in the engine. The chosen 8 units/cell matches existing eight water height steps without treating full cells as sources.

`createLiquidEngine({isLoaded,isOpen,definitions,reactionRules=[],maxCells=8192,maxVisits=256,snapshot=null})`. Mandatory host callbacks `(x,y,z)=>boolean` return literal true only for loaded/eligible cells. Keep them synchronous, side-effect-free and stable during a tick. Use actual shared physical ownership from `src/world-height.mjs` when integrating; isolated kernel rejects Y outside -210..256 inclusive, does not alter legacy generation ceiling or seed. Safe integer world coordinates; no world scans. The cell record is frozen `{x,y,z,id,units,quantities}`; units integer 1..8, absence is empty. Optional extensive quantities (e.g. acid solute or resonance energy, names/units chosen by owners) are nonnegative integer counts, at most eight keys, each <=2^40; key pattern lowercase letter then lowercase letters/digits/hyphens, max 32 chars. Split transfers floor(q*n/originUnits), remainder retained at origin; merge sums, never silently truncates. Capacity/quantity overflow rejects transfer. No implicit creation, destruction or cross-ID blending.

## API
- `insert(x,y,z,id,units,quantities={}) => boolean`: explicit finite external injection; all-or-nothing; loaded/open compatible destination, available capacity. The caller must account for the source resource and only consume it on true. Default is finite; renewable springs/vents are NOT automatically enabled. Future bounded refill policy is an opt-in host adapter; no infinite bucket/source exploit.
- `extract(x,y,z,units) => frozen cell|null`: remove up to requested 1..8 units from a loaded cell; returns removed units/quantities. Can extract a newly obstructed loaded cell to support containment edits. Host must store transferred volume; no silent deletion. For block placement, reject an occupied cell until an atomic displacement plan or extraction succeeds; current kernel does not make world edits. No unsupported automatic displacement or material destruction.
- `getCell(x,y,z) => frozen cell|null`: stored state including unloaded; do not treat this as runtime collision query. `samplePoint(x,y,z) => {cell,fill,surfaceY}|null`: loaded/open flat physical fill sample, half-open vertical boundary. Renderers may sample cell fill and neighbors via getCell plus loaded callbacks; derive display-only slope/current later. Movement/machines use the sample, extraction, insertion interfaces only; no duplicated movement or Resonance machinery.
- `wake(x,y,z)`: enqueue existing liquid in this cell and its six face neighbors after a host block edit, load/unload transition or other relevant change. Unloaded boundaries are impermeable and retained; host must wake the affected loaded boundary cells on reload. No offline catch-up, world scan or automatic cross-chunk generation. Optional owner handoff staging below supports bounded eviction/restore; host integration remains later work.
- `tick(limit=maxVisits) => {visited,moved,changed,pending}`: FIFO bounded by configured maxVisits and initial queue count; gravity first, then fixed +X,+Z,-X,-Z equalization with integer half-difference and total lateral limit. No sideways transfer while a compatible passable cell below can receive gravity flow. Conservative ordered in-place update; deterministic for same input/callback/queue order. A cell may be revisited across ticks; budget is visits, not elapsed time or global fluid time. Changed coordinates are unique for this call, including emptied cells. Caller tracks external insert/extract edits separately. MaxCells is a fail-closed resident-state cap, not production memory qualification. No tick reentrancy; callbacks must not mutate the engine. Failed host callbacks propagate; no transactional recovery for callback exceptions yet.
- `save() => {version:1,cells:[...],pending:[[x,y,z],...]}`: sparse standalone JSON-compatible snapshot including exact FIFO order. Restore with same descriptor/host configuration and `snapshot` argument; unknown version, malformed records, duplicate coordinates or invalid pending references fail closed. Does not alter historical game save schema; adapter, migration, atomic write, capacity admission, unload/rehydration and offline manifest are not integrated. Snapshot cost O(resident cells); no save per tick implied.
- `reactionRules:[{a,b,propose:(aCell,bCell)=>null|{consumeA,consumeB,product}}]`. `proposeReaction(ax,ay,az,bx,by,bz)` finds registered pair in either order, validates adjacent loaded/open unlike cells, calls pure owner rule in declared a/b order and validates exact integer consumption and product tag; returns frozen proposal with original cells or null. Read-only: no consumption, terrain mutation, heat, mixing or automatic dispatch on tick yet. The optional explicit settlement API below validates unchanged input and accounts quantities; host terrain/product adoption remains pending. Lava A owns water-lava semantics; Acid A owns acid/water semantics; other pair rules need explicit ownership/creator approval. No other lane edits the dispatcher.

## Optional Water A source adapter (additive v1)

No engine ABI or shared snapshot change. Each explicit descriptor is `{id,x,y,z,mode,rate,target,initialUnits}`: unique symbolic ID and position, physical coordinates, rate and target 1..8; mode finite requires a nonnegative integer initial stock, renewable requires explicit allowRenewable and omits initialUnits. Empty list is default. No natural placement or automatic tick mount. Call step once per host-authorized simulation step; it visits bounded distinct sources round-robin, never fills above target, uses engine.insert (loaded/open/capacity/identity checks), debits finite stock only on success, reports finite and renewable injections separately and changed coordinates. External renewable injection is explicit, never implied by full cells or elapsed time; policy and rate are reversible proposals. Snapshot v1 holds exact config signature, cursor and stock and rejects changed configuration or invalid stock; host must atomically persist source and engine snapshots together, and ensure a source is not mounted twice or reinitialized on reload. No new source inventory or energy generation; other liquid owners may use their own supply policy through engine.insert. No historical save schema changes.

## Liquid-only displacement (additive v1)
`planDisplacement(x,y,z) => frozen plan|null` computes an all-or-nothing move from an occupied, loaded/open cell to at most six face neighbors, never traverses terrain or mixes liquid IDs. Default order is down, +X, +Z, -X, -Z, up; under a tight resident cap, existing compatible cells precede empty cells (stable within each group). Each destination gets the largest fitting integer amount, trying smaller amounts for quantity limits; remainders stay with the remaining origin until the last transfer. Conservative rejection is allowed instead of an unbounded search. `null` means no plan; for an empty origin the host can separately check placement eligibility. Plan has frozen `origin` and `moves:[{before,after,units}]`; it is private to the engine instance and valid for one commit attempt. Do not serialize, forge, or reuse it.

`commitDisplacement(plan) => {moved,changed}|null` revalidates loaded/open state, exact immutable origin/destination cell identities, and net resident capacity before writing anything. No host callbacks in write phase; no partial liquid moves on rejection. Changes include the emptied origin and all recipients, with normal neighbor wakeups. Host callbacks remain synchronous, pure and stable during planning and commit. The host must acquire its terrain/streaming edit lease, preflight inventory, edit permission, placement and persistence, and coordinate the liquid commit with the terrain edit before any intervening flow. This method does not itself place a block, consume inventory, or make terrain edits atomic; reject placement until the real host transaction can guarantee these. No runtime mount or snapshot format change. Direction and rates remain provisional.

## Sparse physical owner handoff (additive staging v1)
`src/liquids/core/owner-handoff.mjs` exports `LIQUID_OWNER_HANDOFF_VERSION=1` and `createLiquidOwnerHandoff({definitions,reactionRules,isLoaded,isOpen,isOwnerLoaded,maxCells=8192,maxVisits=256,maxParkedCells=8192,maxParkedOwners=64})`. The same engine configuration must be used for validation, staging and eventual adoption. The adapter uses the existing `physicalRegionAt`, `physicalMeshKey` and `physicalSectionBounds` from `src/world-height.mjs`, including negative chunk coordinates, legacy surface, depth and upper section seams; it assigns no new IDs. All callbacks are pure and stable under the host edit/streaming lease. `isOwnerLoaded(owner)` and cell readiness require literal booleans. Budgets are provisional and not GPU or iPhone qualification; configurable hard ceilings are 65,536 resident and parked cells each, 256 parked owners and 4,096 visits.

`stage({state,owner,mode}) => frozen result|null`: state is `{version:1,resident:engine.save(),parked:[{owner,snapshot}]}`; `owner` is the exact canonical physical descriptor `{cx,cz,kind,section,key}` from the existing height module. Mode `detach` requires an owner staged unloaded, all of its resident cells unloaded, no existing parked shard and available parked capacity. Mode `attach` requires an owner staged loaded, its exclusive parked shard (including an explicit empty shard), enough resident capacity and every restored cell loaded/open. Other parked owners must remain unloaded. Malformed snapshots, wrong keys, duplicates, foreign cells or resident/parked overlap throw; unavailable readiness, capacity, missing/duplicate transition or obstruction return null. No caller state is mutated. Success gives `{state,owner,mode,movedCells,movedUnits,boundaryWoken,changed}`. Adopt the whole next state, not only resident cells. Pending order within retained and parked snapshots is preserved; attached pending work is appended after retained FIFO, then restored cells and loaded/open retained face neighbors are enqueued once in stable cell order. No diagonal wakes, offline catch-up, new fluid or automatic terrain generation. `changed` lists removed/restored coordinates; `boundaryWoken` counts newly queued retained face neighbors, including when the owner itself is empty.

This is a bounded transition operation, not per-frame scanning: validation traverses only resident and parked sparse cells/pending arrays within the explicit caps, plus one owner transition. It reuses the existing engine constructor for snapshot validation, not a competing flow solver. Owner shards are temporary storage, not an authorization to change the game save schema. Host must hold an exclusive simulation/streaming/edit lease, stage readiness without exposing it to active simulation, authenticate the current state/owner revision, atomically adopt resident snapshot and parked store together and rebind all source/thermal/render readers to the new engine; discard a stale proposal rather than replay it. On rejection restore previous readiness and leave previous engine/store intact. Atomically persist source state, owner shards and resident snapshot, with historical saves, manifest and installed-PWA tests before runtime mount. Final storage/GPU budgets and integration remain pending.

## Neutral reaction transactions (additive v1)
A registered rule may additionally supply a synchronous pure `settle(proposal) => {routeA,routeB}|null` callback. Existing proposal-only rules remain read-only and cannot execute by accident. Each nonzero consumed portion must route in its entirety to the opposite cell (routeA "b", routeB "a") or to the explicit product-input receipt ("product"); zero consumption requires null. Missing/invalid routing never implicitly discards mass. No new liquid IDs, chemistry, block IDs or resource policy are defined by the core.

`planReaction(ax,ay,az,bx,by,bz)` uses existing registered dispatch, owner-declared pair ordering, and current loaded/open adjacency. Returns a frozen transient engine-instance plan or null. Fields: proposal, routeA, routeB, takenA/takenB (exact consumed cell records or null), afterA/afterB (replacement records or null), product (symbolic owner tag), productInputs (frozen array of exact consumed records routed to the product ledger). Existing split rounding retains the remainder with the original cell; every integer unit and extensive quantity is accounted for. Transfers preserve the receiver identity and reject volume/key/quantity overflow. No cell or FIFO mutation during planning.

`commitReaction(plan)` is a single attempt; revalidates original cell identities, loaded/open state, and owner proposal/routing before any write, rejects stale/foreign/forged/reused plans. Returns frozen {product,productInputs,changed} or null. The two-cell liquid mutation has no host callbacks in its write phase, with normal FIFO wakes and no write to unchanged participants. Complexity bounded by two cells/eight keys per cell; no scans and no automatic reaction tick. Rules and host readiness must be pure and stable under an exclusive host simulation/edit lease; callbacks must never mutate the engine. Malformed owner policy throws, unavailable/stale capacity or eligibility returns null. Do not serialize plans.

Product inputs are an accounting receipt, not placed blocks, steam entities or inventory output. Host must preflight permission, owner product mapping and persistence, stage on an isolated engine and adopt new liquid state and durable product/terrain ledger together (or equivalent atomic transaction). Do not invoke live commit if receipt retention or host transaction cannot be guaranteed. No host adoption, product conversion, reaction scheduling, damage or fire is implemented. Lava A and Acid A retain their rule semantics: owner adapters may opt into product routing for quench or transfer routing for dilution after reviewing their exact existing policies. Neither owner's existing proposal is automatically executable. Pinned owner integration tests, creator gameplay approval and full host qualification are pending.

## Optional Water A freeze/thaw staging (additive v1)
`src/liquids/water/physics/phase.mjs` exports `WATER_PHASE_VERSION=1` and `createWaterPhaseTransitions({definitions,reactionRules,isLoaded,isOpen,temperatureAt,canFreeze,canThaw,allowFreeze=false,allowThaw=false,freezeAt=0,thawAt=2,maxCells=8192,maxVisits=256,maxFrozenCells=8192})`. Both directions disabled by default; finite host temperature values and separate hysteresis thresholds are provisional, not final weather or climate policy. Only full eight-unit water cells may freeze. Other liquid identities and partial water are unaffected. Frozen entries retain the exact original water record, including every extensive quantity; they are a solid-phase accounting ledger, not a sixth liquid, new numeric block ID, or inventory reward. No latent heat exchange, ambient damage, automatic freezing, mining behavior, or ice terrain mapping is implied.

`validate(state)` validates/canonicalizes `{version:1,resident:engine.save(),frozen:[waterCell,...]}` with the existing engine record validator, rejects duplicate frozen positions, resident overlap, malformed quantities, and over-budget snapshots. `stage({state,x,y,z,mode:'freeze'|'thaw'})` returns an immutable `{state,mode,water,changed}` or null. It operates on a private reconstructed engine, never the live engine or caller snapshot. Loaded/open eligibility must be literal true in the staged terrain view; canFreeze must confirm authorized whole-cell freezing, canThaw must confirm the exact ledger-backed ice voxel is eligible for removal and its replacement space is open. Freeze extracts the entire water record to the ledger, thaw reinserts the exact record into an empty cell; failed capacity/permission/temperature or duplicate transitions on successor state leave all input untouched. The existing core handles pending FIFO retirement and wakeups. No new flow engine or host callbacks during a live write. Malformed state throws.

This is bounded snapshot staging (O(resident+frozen), hard caps 65,536 each), not a per-frame scan or qualified runtime thermal scheduler. The host must hold its exclusive edit/streaming lease, authenticate current complete state revision and terrain identity, ensure no overlapping parked owner liquid or frozen-cell injection, stage the correct terrain readiness, and atomically adopt resident, parked, frozen, sources, product ledger and physical terrain state together; do not replay stale results or install the returned resident alone. A thaw plan is only usable with the corresponding real ice removal, and freezing must block later liquid insertion into that physical voxel. Validate all ledgers together before persistence. Retain historical game save schema untouched until a coordinated migration/host adapter is approved. No player-facing activation or policy approval is implied; measured budgets and integrated terrain/PWA/iPhone tests remain pending.

## Unified liquid persistence staging (additive v1)
`src/liquids/core/persistence.mjs` exports `LIQUID_PERSISTENCE_VERSION=1` and `createLiquidPersistence({worldId,policyId,definitions,reactionRules,waterSourceOptions,maxCells,maxVisits,maxParkedCells,maxParkedOwners,maxFrozenCells,maxProducts,maxRecords,maxChars})`. This is a sidecar codec, not a game save schema, file/storage writer, new world mode, or a claim of historical game migration. Host supplies a stable world identity and versioned policy identity (lowercase alphanumeric/hyphen tokens, up to 128 characters) covering definitions, owner rules, source configuration and host persistence semantics. Existing engine, source and owner validators are reused; the owner-handoff adapter now also exposes pure `validate(state)` returning canonical immutable resident/parked snapshots without changing readiness or simulating anything.

Envelope: `{version:1,worldId,policyId,revision,resident,parked,frozen,waterSources,products}`. Revision is a nonnegative safe integer assigned by the host. Resident and parked arrays preserve exact FIFO, physical owner identity and all integer quantities. Frozen entries are full water cells, exclusive of actual liquid coordinates even in parked shards; frozen cells may occupy other coordinates in a parked owner. Water source snapshot must be present and match the exact configured signature/stock bounds; no silent replenishment. Products are unconverted accounting receipts `{id,product,productInputs}` with unique host-assigned identity and one or two exact consumed cell records, no implicit terrain/loot conversion. Two inputs must be adjacent unlike liquids; historical receipt coordinates may recur across transactions and may now contain liquid. Transfer-only reactions with no product inputs require no receipt row. No other lane-specific source, thermal or product conversion policy is mounted; additional owner ledgers require coordinated future versioning.

`validate(state)` returns a canonical frozen copy; `encode(state)` returns JSON text; `decode(text)` rejects unknown versions, incompatible identities, missing/unknown fields, duplicate/overlapping liquid storage, malformed records or exceeded budgets. Individual caps reuse existing resident/parked limits, plus default 8192 frozen cells, 4096 product receipts, 32768 aggregate cell/input records and 8 Mi UTF-16 code units of serialized text (canonical ASCII); all configurable with hard ceilings. No truncation; decode preflights text length before parsing. These are staging bounds, not measured device memory or frame budgets. `migrateEngineSnapshot(resident)` explicitly imports only the isolated v1 engine snapshot when no sources are configured; it rejects game-save documents, unknown versions and configured-source migration without an explicit ledger. No implicit conversion of historical game water blocks or bytes.

The codec does not authenticate the save, enforce monotonic revisions across calls, or prove the historic provenance of valid-shaped source stock/receipt entries. Host must verify expected prior revision/world/policy and integrity, preserve original game-save bytes, stage all participating owner states and physical terrain, then atomically adopt or reject the complete state under one lease with previous-good rollback. It must never reapply receipt IDs or restore a stale snapshot as fresh progress. Actual storage, migration from historical game saves, other owner ledgers, legacy terrain/ice/product mapping and integrated performance/PWA qualification remain pending. No production integration or numerical IDs.
