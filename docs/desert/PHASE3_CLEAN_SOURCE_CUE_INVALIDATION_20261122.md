## Real defect: one-block edit batches fail to refresh a three-block visual cue
- Original `src/chunks.mjs::editAffectedChunks(x,z)` refreshes owner + adjacent chunks only when the edit is on exact outermost 0/15 local coordinate. That is correct for one-block physical geometry, but source-guarded M7 3-block **color** cues can affect RGB in another chunk when an edit is 2–3 blocks inside the original owner. A published adjacent mesh would retain stale color after genuine mining/placement.
- New `desertSeamEditAffectedChunks(world,x,z,y)` preserves every legacy `editAffectedChunks` member, and additionally computes radius3 horizontal source-center coverage using `chunkCoord(x+.5±3),chunkCoord(z+.5±3)`. Includes diagonal chunk if both axes are near chunk edges, with at most five deduplicated chunks including all old geometry neighbors; edits outside these neighborhoods do not expand. The caller retains the original all-buffers-before-publish edit batching, depth-section behavior, upload rollback and save logic.
- The function falls back unchanged for legacy M6/v2-v5, non-M7, original protected/empty columns, non-original-top Y (ordinary buried digging), and source caps other than 401 or qualifying original low-weight Desert 258. M7 world can be bare `FourRegionWorld` or the actual Pack2 `world.base` wrapper. It does **not** mutate original plans, edit states, world generation, or general chunk API.
- The new edit dispatch is conservative for original scree401 edits because scree from any climate can feed an authentic Desert-side cue. It must not incorrectly reject an original 401 before evaluating a neighboring Desert hardpan. The resulting small extra rebuild budget near some original surface edits is still **unmeasured on physical iPhone**.
